# Topic: Cloud, infrastructure, and CDR

## Meta-Summary

The records portray cloud security as a problem of **composed trust boundaries**, not merely vulnerable virtual machines or bad configurations. The highest-impact findings occur where cloud services combine tenant isolation, managed identities, automation, containers, orchestration, shared control planes, and provider-operated middleware. A low-privileged workload or apparently benign API operation can inherit authority from a more privileged service, cross tenant boundaries, or expose provider-wide infrastructure. Representative cases include privilege hijacking between Amazon ECS tasks [record_id:38], Azure API Connections leaking secrets across tenants [record_id:15], managed-identity confused-deputy chains in Azure and GCP [record_id:2684], and sandbox escapes leading to cloud-wide or cross-tenant compromise [record_id:75] [record_id:2630] [record_id:2668].

Containers and Kubernetes remain central. The records cover kernel and GPU-based container escapes, namespace isolation failures, weak admission policy, incomplete syscall controls, insecure debugging, and attacks on orchestration frameworks. The defensive direction is toward layered prevention—admission control, runtime enforcement, seccomp or stateful syscall filtering, workload identity, inventory, and exposure monitoring—rather than relying on post-deployment alerts alone [record_id:2429] [record_id:2456] [record_id:2617] [record_id:2679].

Cloud detection and response (CDR) appears less as a single product category than as a collection of operational capabilities: audit-log analysis, principal behavior baselining, service attribution, attack-path graphing, cloud inventory interrogation, internet exposure monitoring, and multi-source telemetry correlation. The strongest operational examples include Kubernetes audit-log graph modeling [record_id:153], AWS principal baselines [record_id:2813], GCP Workload Identity Federation hunting [record_id:2787], shadow-cloud scoping with Luminaut [record_id:2414], and hybrid-cloud egress attribution using proxy, eBPF, and container signals [record_id:2761].

A major 2026 trend is the fusion of cloud and AI infrastructure. AI sandboxes, gateways, agents, inference endpoints, GPU clusters, and managed tools inherit traditional cloud risks while adding prompt-driven tool use, non-deterministic identities, and new shared-runtime boundaries. These records repeatedly show that prompt injection becomes materially dangerous when it reaches cloud credentials, code execution, management APIs, or cross-tenant infrastructure [record_id:2606] [record_id:2662] [record_id:2934] [record_id:2951]. At the same time, AI is described as accelerating both cloud attack operations and defensive analysis [record_id:2355] [record_id:118].

## Research Landscape

The collection spans 2018–2026, but it is heavily concentrated in 2025 and 2026 conference abstracts from Black Hat, DEF CON, BSides Las Vegas, CAMLIS, Prompt\|\|GTFO, and [un]prompted. Earlier CAMLIS records emphasize building scalable security-data and machine-learning infrastructure on AWS, Snowflake, ECS, Kubernetes, and serverless systems [record_id:214] [record_id:235] [record_id:157]. The later material shifts strongly toward offensive cloud research, including cross-tenant vulnerabilities, control-plane exploitation, container escapes, machine-identity abuse, cloud-service weaponization, and AI-infrastructure compromise.

The dominant source type is a talk description rather than a full paper, code repository, or independently reproduced technical report. Many records promise live demonstrations, tools, proof-of-concept code, or concrete case studies, but the supplied text generally does not contain enough implementation detail to reproduce the results. Evidence is strongest where a record identifies a CVE, specific affected services, measured populations, forensic artifacts, or observed campaigns. Examples include the Postgres RCE CVE-2024-10979 [record_id:2063] [record_id:2528], Azure Automation CVE-2025-29827 [record_id:2672], ESXi escape CVEs and in-the-wild exploitation [record_id:40], a claimed 230,000 exposed Ray servers [record_id:2642], and a honeypot’s measured AI-infrastructure probes [record_id:3012].

The research area is broad and overlaps several adjacent disciplines:

- **Cloud-platform security:** Azure, AWS, and GCP APIs, managed identities, databases, CloudShell, IAP, and provider control planes.
- **Cloud-native and container security:** Kubernetes, ECS, OCI registries, seccomp, syscall enforcement, namespace isolation, and GPU runtimes.
- **Cloud operations and CDR:** logging, baselining, scoping, exposure discovery, attack-path analysis, and incident response.
- **Infrastructure and middleware:** VMware, Kafka, Airflow, Teleport, Windows clustering, ZTNA/SASE, and distributed data systems.
- **Cloud-delivered supply chains:** container registries, abandoned S3 buckets, Nix/NixOS, dangling DNS, webhooks, and CI/CD.
- **AI infrastructure:** agent sandboxes, MCP, LLM gateways, inference services, GPU clusters, and confidential AI.
- **Hybrid and cyber-physical backends:** cellular IoT, solar systems, and maritime platforms whose cloud control planes reach physical devices.

There is relatively little explicit discussion of commercial CNAPP or CSPM products. Instead, the collection emphasizes open-source tooling, provider-native APIs, and bespoke investigative systems. It therefore offers stronger evidence about the underlying problems that CNAPP/CDR systems must solve than about comparative product effectiveness.

## Major Themes And Trends

### Cloud trust is transitive, hidden, and frequently overprivileged

The most persistent theme is that cloud authority flows through service composition. Managed services often possess permissions that their users do not, making them potential confused deputies. Azure API Connections can expose connected systems and token stores to low-privileged or cross-tenant attackers [record_id:15]. Azure Automation flaws reportedly allowed managed-identity takeover across tenants [record_id:2672]. A broader analysis claims the same structural pattern recurs across Azure and GCP: a user invokes a platform service whose managed identity has excessive rights, turning legitimate service operations into privilege escalation [record_id:2684].

GCP service agents are similarly presented as a fertile privilege-escalation surface [record_id:2715]. Google Cloud IAP can fail as a boundary through permissive IAM, trusted headers, overlooked endpoints, or a claimed vulnerability allowing exfiltration without public IP traffic [record_id:2495]. In hybrid Microsoft environments, undocumented trust paths from Active Directory to Entra ID can bypass authentication or MFA and leave weak logging [record_id:76]. OAuth implementation errors also blur authentication and authorization, with one record claiming access to more than 20 internal Microsoft applications [record_id:20].

This trust problem extends beyond human accounts. Long-lived machine credentials, service accounts, OAuth applications, Kubernetes identities, CI/CD secrets, and agent credentials are described as fragmented and poorly governed [record_id:2620]. CSP-managed non-human identities differ across providers and require provider-specific threat modeling [record_id:2552]. The records increasingly advocate short-lived federation and workload identity rather than static secrets [record_id:2396] [record_id:2468], while warning that “keyless” designs still create persistence opportunities if federation pools, providers, or bindings are misconfigured [record_id:2787].

By 2026, AI agents are framed as a new kind of machine identity: autonomous, non-deterministic, inherited from CI/CD or internal tools, and difficult to assign to an owner [record_id:2817]. This broadens the access-control question from “who has access?” to “what system is acting, under whose authority, with which tools and contextual constraints?”

### Multi-tenancy repeatedly fails at the layers surrounding the advertised boundary

Cross-tenant and container-isolation failures recur across almost every infrastructure layer. Amazon ECS’s shared EC2 hosts allegedly allowed a low-privileged task to hijack the IAM roles of colocated higher-privileged containers through an undocumented protocol [record_id:38]. A flaw in the NVIDIA Container Toolkit enabled container-to-host escape and, in some cases, Kubernetes-cluster or cross-tenant compromise across major AI platforms [record_id:75]. Later GPU research describes a Linux kernel-module use-after-free yielding container escape and host root [record_id:2952].

Managed Kubernetes is vulnerable both below and above the container boundary. A Linux networking bug reportedly allowed escalation from a default pod to node compromise on two managed cloud providers [record_id:2678]. At the platform layer, vulnerabilities in Kubeflow, Istio, and Traefik allegedly violated namespace and workload boundaries despite Pod Security Standards, Network Policies, and admission controls [record_id:2679]. Even ordinary cluster configurations can enable surprising disruption [record_id:2446].

The same pattern appears in non-Kubernetes sandboxes. Cloudflare CodeMode and Workers relied on V8 isolates, but vulnerabilities in the native JSG “glue” layer allegedly enabled host code execution and cross-tenant private-key extraction [record_id:2630]. An unnamed managed database service was reportedly compromised through a custom .NET sandbox escape, lateral movement, and extraction of a master key covering every customer database [record_id:2668]. Copilot’s Azure-backed code execution environment was allegedly escaped through privilege escalation and an ACR Image Streaming flaw [record_id:2606]. ChatGPT’s isolated container is described as vulnerable through file parsing, reasoning-channel manipulation, scheduler abuse, and a shared package-manager side channel [record_id:2645].

The common lesson is that the visible sandbox—container, namespace, V8 isolate, language runtime, or enclave—is only one component of the boundary. Native glue code, metadata endpoints, shared package services, network topology, boot inputs, service identities, and policy-loading timing are equally important.

### Prevention and runtime containment are moving closer to workload launch

Several records reject a purely alert-driven Kubernetes strategy. Kyverno is proposed for rejecting dangerous workloads before deployment, while KubeArmor enforces runtime behavior without requiring application changes [record_id:2429]. Seccomp remains a practical containment mechanism, with profile generation and tuning demonstrated against an Apache Druid exploit [record_id:2456]. A secure Kubernetes debugging tool, Dallas Debugger, seeks to give developers operational access without weakening clusters, using in-memory execution, no disk writes, CIS-oriented controls, and security-by-design principles [record_id:2218].

At the same time, existing syscall defenses are criticized as too static or too late. One record argues that per-syscall filters miss sequence-dependent attacks, signal-based termination can occur after a malicious kernel operation completes, and operator-loaded policy creates an initialization race. Its proposed replacement combines thread-level sequential evaluation, inline LSM-BPF denial, and OCI hooks for atomic policy installation [record_id:2617].

The broader trend is from one-time scanning toward **continuous and layered enforcement**: CI and pre-commit checks [record_id:2440], infrastructure-as-code controls [record_id:2396], admission-time policy [record_id:2429], syscall-level enforcement [record_id:2456] [record_id:2617], and service-level egress governance [record_id:2761].

### Visibility, attribution, and context are the core of cloud detection and response

Cloud environments produce abundant telemetry but weak answers to basic investigative questions: what exists, what is exposed, who initiated activity, and whether an API call is malicious or expected.

Several records address inventory and exposure. Luminaut combines internal cloud scanning, audit-log timelines, and external scanner context to scope forgotten AWS and GCP deployments [record_id:2414]. Another framework uses cloud inventory APIs such as AWS Config to identify dynamic exposure faster than traditional IP-based scanners [record_id:2756]. Internet-scale scanning is also used to model vendor concentration and cascading systemic risk [record_id:66].

Identity telemetry is especially important. AWS Threat Hunter builds an individualized behavioral baseline for each IAM principal rather than treating all API events uniformly [record_id:2813]. GCP WIF hunting relies on recognizing insecure pool conditions, provider modifications, certificate trust, and the difference between freely available setup logs and paid credential-use logs [record_id:2787]. Identity-first emulation across AD, Entra, SaaS, and cloud control planes is proposed as a purple-team method for validating expected telemetry and failure points [record_id:3017].

Kubernetes audit logs support graph-based detection because they include activity and metadata such as IP and user agent. One CAMLIS study models dependent events in a session as a graph, derives GNN embeddings, and uses those embeddings to strengthen anomaly detection around simulated adversarial behavior [record_id:153]. At a larger architectural scale, RIG-RAG converts cloud configuration into a security-enriched knowledge graph for natural-language infrastructure reasoning [record_id:118], while MeshLens combines routes, container specifications, semantic source-code graphs, runtime metadata, and LLM-derived intent labels to map an external request to executing code [record_id:3130].

Egress attribution is another recurring gap. Shared proxies, NAT, and ephemeral compute can obscure which workload contacted a suspicious domain. Combining proxy logs, eBPF telemetry, and container metadata is proposed as a practical basis for service attribution, allowlist evolution, and human-reviewed domain governance [record_id:2761].

### Legitimate cloud services are increasingly used as attack infrastructure

Attackers can hide behind services enterprises cannot easily block. Google Calendar and other Google services can carry C2 or SOCKS traffic [record_id:2097]. Distributed storage systems such as IPFS, Codex, and Cloudflare R2 can host payloads, commands, or phishing artifacts with takedown resilience [record_id:1896]. Azure Relay, AWS IoT Secure Tunneling, and AWS IoT Core MQTT can broker C2 through trusted service domains and ordinary outbound HTTPS or WebSockets [record_id:3040].

CloudShell is a particularly notable abuse surface. Research across AWS, Azure, and GCP identifies persistent home directories, reset-resistant access, revocation-surviving WebSockets, permissive defaults, and ways to build distributed C2, staging, exfiltration, or compute networks [record_id:2809] [record_id:2888]. Bare-metal clouds add provisioning, firmware, and network weaknesses that can support persistence or multi-tenant compromise [record_id:1955].

The same trusted-infrastructure issue appears in operational relay networks [record_id:2025], cloud-based open relays used for phishing [record_id:2698], and exposed AI inference services used as someone else’s reconnaissance or post-exploitation compute [record_id:3119]. This makes coarse domain blocking ineffective and increases the value of behavioral analysis, service attribution, tenant-aware telemetry, and endpoint controls.

### Infrastructure abandonment and lifecycle failures are scalable supply-chain risks

Several records focus less on a live exploit than on resources that outlive their owners. Abandoned S3 buckets referenced by software artifacts could support a massive supply-chain compromise; the described 5,155-bucket scenario was prevented rather than observed, but the research argues that big-data tooling and LLM agents can scale discovery and exploitation [record_id:1972] [record_id:2134]. Dangling DNS records persist in multi-account AWS environments because ownership is unclear and teardown processes do not remove dependent records; Ghost Records combines Elastic IP inventory and Route53 analysis and recommends IaC cleanup hooks [record_id:2829].

“Shadow webhooks” present a related lifecycle problem: Slack, Teams, Jira, GitHub, CI/CD, and monitoring integrations remain active after destinations or owners disappear, potentially leaking events or allowing forged messages [record_id:3014]. Airflow instances similarly accumulate credentials and executable DAGs while being treated as ordinary applications instead of production control planes [record_id:2771].

Defensive supply-chain records advocate reproducibility and traceability. Nix and NixOS are presented as alternatives to opaque SaaS dependencies, vendor lock-in, and Docker image decay [record_id:1954] [record_id:2130]. Open-source code-to-cloud pipelines combine Trivy, GitLeaks, Checkov, ZAP, and OpenGrep across IDE, pre-commit, and CI/CD stages [record_id:2440]. Container vulnerability management can also use SBOMs, source, documentation, VEX categories, RAG, and tool-using LLM agents to distinguish actionable CVEs from false triggers [record_id:138]. Scanning Google-owned Artifact Registry images for secrets and vulnerabilities highlights that provider ownership does not itself establish artifact safety [record_id:2467].

### AI infrastructure is becoming ordinary cloud infrastructure—and an unusually powerful attack surface

The later records treat AI gateways, agents, inference services, and GPU orchestration as production infrastructure. LiteLLM, described as a widely deployed AI gateway, allegedly exposed authentication bypass, root RCE, SSRF to cloud credentials, and poor real-world authentication hygiene [record_id:2934]. Exposed MCP servers, local inference APIs, and AI gateways are already receiving framework-aware reconnaissance and credential probes [record_id:3012]. ShadowRay 2.0 allegedly abused legitimate Ray orchestration features to spread across exposed AI servers, mine cryptocurrency on GPUs, and remove competing attackers [record_id:2642].

AI agents can also convert indirect text into cloud actions. One record describes Cloudflare WAF logs and Sentry stack traces as prompt-injection carriers that compromise agents and then alter DNS, poison recommendations, or move agent-to-agent [record_id:2951]. Managed agent platforms and SDKs can expose credentials when an attacker bypasses the model and directly invokes tools [record_id:2662]. Security testing of YC agents found recurring IDOR, sandbox escape, metadata access, SSRF, and Git credential leakage [record_id:2209].

AI is simultaneously an operational accelerator. An observed AWS incident allegedly moved from stolen credentials to administrator access in eight minutes, compressing familiar techniques beyond traditional response timelines [record_id:2355]. Test-time compute is being evaluated to improve consistency in container vulnerability analysis and server-alert triage [record_id:117]. Agentic cloud reasoning systems are being built around infrastructure graphs [record_id:118]. This creates a race: attackers automate reconnaissance and privilege expansion while defenders use agents to analyze larger and more complex estates.

### Confidential computing helps, but only if the deployment trust model is complete

Confidential AI uses TEEs and remote attestation to protect prompts, models, and data during computation in public or hybrid clouds [record_id:2343]. Cove extends this concept into multi-stage workflows in which enclave outputs and downstream processing are gated by cryptographically verifiable certificates [record_id:3088].

Other records challenge assumptions around this protection. Nitro Enclave attacks target boot-time inputs—object storage, environment variables, and insufficiently attestation-bound KMS policies—that are not covered by an otherwise valid enclave measurement [record_id:2919]. A separate physical attack uses DDR5 bus interposition against server-grade TEE deployments that lack integrity and replay protections assumed by users [record_id:2935]. Together, these show that attestation can accurately describe a measured image while failing to guarantee the safety of deployment inputs, key release, memory integrity, or surrounding infrastructure.

## Methods, Tools, And Approaches Discussed

The collection contains several recurring research and operational methods.

**Black-box and architectural cloud-service research** begins by mapping hidden APIs, tokens, handlers, sandboxes, and internal trust relationships. Azure API Connections research traverses ARM, API Management, custom connectors, consent servers, and token stores [record_id:15]. Cloudflare research isolates the workerd/JSG boundary rather than focusing only on V8 [record_id:2630]. CloudShell research reverse-engineers private REST, WebSocket, browser authentication, and credential flows [record_id:2809] [record_id:2888]. Similar architectural examination is applied to Teleport clusters [record_id:2615], ZTNA/SASE clients and IPC [record_id:2062], Kafka brokers and ecosystem components [record_id:1993], and Azure Automation handler logic [record_id:2672].

**Attack-path and identity graphing** is used to expose transitive cloud authority. SecBridge, Cartography, and AWSPX are cited for environment mapping and IAM visualization [record_id:2484]. NHI-Hound is intended to discover and graph machine identities and trust relationships across cloud, SaaS, CI/CD, Kubernetes, and AI environments [record_id:2620]. RIG-RAG enriches configuration graphs for LLM-assisted reasoning [record_id:118], while MeshLens stitches network routes to source code and runtime behavior [record_id:3130].

**Telemetry correlation and baselining** move detection away from single-event signatures. Kubernetes sessions become event graphs and GNN embeddings [record_id:153]. AWS API behavior is modeled per principal to identify personalized deviations [record_id:2813]. Proxy logs, eBPF signals, and container metadata are combined for egress attribution [record_id:2761]. Cloud inventory, audit timelines, and external observations are fused for incident scoping [record_id:2414]. Large-scale internet scanning supports both systemic-risk mapping [record_id:66] and exposure or abuse measurement [record_id:3012].

**Policy-as-code and preventive controls** include Terraform-based cross-cloud workload identity [record_id:2396], YAML admission and runtime policies through Kyverno and KubeArmor [record_id:2429], seccomp profiles generated with tools such as Kubescape [record_id:2456], and IaC teardown hooks for DNS cleanup [record_id:2829]. Code-to-cloud pipelines integrate Trivy, GitLeaks, Checkov, ZAP, and OpenGrep [record_id:2440].

**Scalable security-data architecture** is represented by AWS SQS, S3 replication, spot-instance clusters, Redshift, and DynamoDB for malware labeling and historical evaluation [record_id:214]; AWS serverless container processing for binary feature extraction [record_id:235]; and Snowflake-centered SQL workflows connected to autoscaling ECS or Kubernetes components [record_id:157]. These records emphasize batching, immutability, historical reproducibility, low operational overhead, and data quality.

**Offensive simulation and purple teaming** appear in the four-part AWS/Azure/GCP workshop using RedCloud OS and APT-style TTPs [record_id:2489] [record_id:2490] [record_id:2491] [record_id:2492]. Identity-first playbooks provide expected telemetry and scoring [record_id:3017]. Russian APT adoption of public offensive research is used to argue that defenders should track new red-team techniques quickly [record_id:2024].

**Containment and hardening** span workload placement, syscall restriction, and stronger isolation. ECS guidance discourages mixing low- and high-privilege tasks on the same host [record_id:38]. Seccomp and its proposed stateful successor restrict or preempt dangerous operations [record_id:2456] [record_id:2617]. Confidential-computing records add attestation-gated keys and verifiable workflow composition [record_id:3088], while sandbox-focused discussion argues that highly capable agents may eventually require protection models drawn from national-security systems rather than ordinary Linux namespaces [record_id:3129].

## Notable Talks, Records, And Evidence

Several records are especially representative of the collection’s findings.

**ECS-cape** is a concise demonstration of how shared container hosts and undocumented cloud protocols can invalidate IAM isolation. Its importance lies in connecting container placement directly to cloud authorization, rather than treating it only as a host-security issue [record_id:38].

**Breaking Out of the AI Cage** links an NVIDIA Container Toolkit vulnerability to major AI platforms, Kubernetes compromise, credentials, customer data, and cross-tenant access. It is a pivotal bridge between conventional container security and the newer AI-infrastructure theme [record_id:75].

**Trust No Deputy** elevates individual managed-identity bugs into a systemic cloud vulnerability class. Its claim that malicious and legitimate service operations are forensically difficult to distinguish is especially consequential for CDR design [record_id:2684]. The same operational problem appears in “Administrative Living-off-the-Land,” where attackers use legitimate CI/CD, IAM, cloud-control-plane, and security-tool APIs so successfully that detection becomes a question of intent [record_id:2718].

**The Crypto Caper** is the collection’s clearest multi-cloud incident-response narrative. It follows a compromise from help-desk phishing through an identity provider, GitHub, and production AWS to repeated cryptocurrency theft, illustrating why cloud incidents must be scoped across identity, source control, and multiple providers rather than investigated as isolated account events [record_id:2599].

**Stateful syscall defense** is one of the most technically specific defensive proposals. It does not merely recommend seccomp; it identifies sequence blindness, delayed enforcement, and startup races, then proposes thread-state tracking, LSM-BPF interception, and OCI-hook policy injection [record_id:2617].

**GCP WIF abuse detection** is unusually useful for practitioners because it pairs three concrete attack patterns with audit trails, hunting queries, and an explicit cost-versus-coverage problem [record_id:2787]. Likewise, AWS principal baselining describes a practical move from global rules toward identity-specific behavior models [record_id:2813].

**CloudShell exploitation** is supported by related BSides and DEF CON records. The research claims reproducible, cross-provider abuse and releases CloudBasher for enumeration, persistence, distributed compute, C2, networking, and exfiltration [record_id:2809] [record_id:2888]. The overlap strengthens confidence that this is a developed body of work, although the abstracts alone do not establish vendor remediation status.

**ShadowRay 2.0** is one of the strongest in-the-wild claims: a self-propagating campaign targeting Ray across more than 230,000 exposed servers, with attack artifacts, evolving payloads, GPU miners, and anti-competitor scripts [record_id:2642]. Its quantitative claims and reference to real artifacts make it more evidentially substantial than purely hypothetical attack scenarios, though independent corroboration is not present in the supplied record.

**The confidential-computing records** provide a useful internal debate. Confidential AI and Cove describe constructive TEE architectures [record_id:2343] [record_id:3088], while the Nitro Enclave and DDR5 attacks show that a valid attestation can coexist with unsafe inputs or weak physical integrity [record_id:2919] [record_id:2935].

**Historical infrastructure records** provide important context. The AWS malware-labeling architecture emphasizes time-aware labels, rollback, GDPR, and affordable regional data processing [record_id:214]. The SQL-driven Snowflake/ECS/Kubernetes design argues that centrally stored cloud data enables cross-estate detection and remediation while reducing MLOps complexity [record_id:157]. These records show how cloud security operations evolved before the later emphasis on cross-tenant offensive research.

## Gaps, Limits, And Open Questions

The primary limitation is evidentiary. Most records are conference descriptions that state intended demonstrations or findings rather than supplying full technical detail. Claims of cross-tenant impact, affected populations, “first-ever” exploitation, or provider-wide compromise should be validated against papers, advisories, patches, code, and vendor statements. This is especially important for 2026 records describing future conference sessions.

The corpus does not systematically compare cloud providers’ logging quality, default retention, cost, or event semantics. The GCP WIF record explicitly identifies paid log tiers as a detection barrier [record_id:2787], but equivalent analysis for Azure and AWS is sparse. Open questions include:

- Which attack paths are visible in default logs, and which require premium data sources?
- How quickly can identity, CI/CD, control-plane, and workload telemetry be normalized during a multi-cloud incident?
- How can defenders distinguish malicious use of legitimate managed identities or administrative APIs from routine automation?
- What minimum telemetry survives a cross-tenant or provider-internal compromise?

There is little direct evaluation of CNAPP, CSPM, CIEM, or commercial CDR products. The records identify capabilities these platforms should provide—inventory, identity graphing, attack-path analysis, workload telemetry, runtime controls, and response—but do not establish which products detect the described attacks or at what false-positive cost.

Defensive proposals often lack longitudinal production measurements. The records do not quantify the operational burden of maintaining Kyverno, KubeArmor, seccomp, LSM-BPF, egress allowlists, behavior baselines, or graph-based inventories in rapidly changing environments. It remains unclear how these approaches affect performance, developer workflows, and alert volume at large scale.

The relationship between prevention and response remains unsettled. Admission and syscall controls can stop known dangerous behavior, but kernel, GPU, glue-code, and managed-service vulnerabilities repeatedly bypass expected boundaries. Conversely, legitimate administrative API abuse can evade behavior controls without exploiting a vulnerability. Future research should explore how policy, hardware isolation, identity context, provenance, and high-fidelity telemetry can reinforce one another.

AI-related records pose additional unanswered questions:

- How should cloud identity systems represent autonomous agents and delegated tool calls?
- Can an organization establish an auditable chain from user intent through model reasoning to each cloud API action?
- What isolation model is appropriate when agents can discover novel kernel or runtime vulnerabilities [record_id:3129]?
- How should cloud providers detect stolen or exposed inference capacity without blocking legitimate public endpoints?
- Can prompt-origin provenance survive transfers through logs, tickets, MCP tools, and other agents?

Finally, systemic cloud risk is discussed through internet scanning and disclosure-program strain [record_id:66] [record_id:2974], but the corpus lacks a common model for quantifying cross-service blast radius, provider concentration, shared middleware dependencies, and remediation latency.

## Coverage And Evidence Notes

The core 2025 Black Hat material covers Windows failover-cluster credentials, Kerberos, lateral movement, and domain compromise [record_id:10]; Azure API integration and token-store abuse [record_id:15]; Entra OAuth authorization errors [record_id:20]; ECS IAM-role hijacking [record_id:38]; ESXi escape and failed patching [record_id:40]; cellular IoT pivots into cloud backends [record_id:44]; internet-scale systemic-risk mapping [record_id:66]; NVIDIA container escape across AI clouds [record_id:75]; and hybrid AD-to-Entra lateral movement [record_id:76]. Of these, the clustering, VMware, and IoT records are infrastructure-adjacent rather than cloud-operations studies, but they matter because they show how enterprise, virtualization, and device trust can become paths into cloud or backend environments.

The CAMLIS records supply the collection’s main data-engineering and machine-learning perspective: test-time compute for container-vulnerability and server-alert agents [record_id:117], GraphRAG-style cloud reasoning [record_id:118], LLM-assisted CVE and VEX analysis for containers [record_id:138], GNN embeddings over Kubernetes audit logs [record_id:153], SQL-driven cloud detection infrastructure [record_id:157], AWS malware-labeling infrastructure [record_id:214], and serverless AWS binary-analysis pipelines [record_id:235]. These are mostly system descriptions and reported evaluations rather than raw datasets.

The DEF CON 33 material broadens the attack surface to distributed storage used for C2 and phishing [record_id:1896], GRE/VxLAN tunnel hijacking [record_id:1907], bare-metal cloud compromise [record_id:1955], solar-cloud APIs and shared OEM infrastructure [record_id:1978], Kafka-server RCE affecting cloud providers [record_id:1993], monitoring potential abuse of cloud quantum platforms [record_id:1996], cloud-focused APT tradecraft [record_id:2024], operational relay networks using named cloud providers [record_id:2025], ZTNA/SASE compromise [record_id:2062], managed Postgres RCE [record_id:2063], and Google-service C2 [record_id:2097]. Nix dependency-management descriptions appear twice with substantially overlapping text [record_id:1954] [record_id:2130], as do the abandoned-S3-bucket supply-chain scenario records [record_id:1972] [record_id:2134]. These duplicates reinforce event coverage but should not be counted as independent findings.

Prompt\|\|GTFO contributes empirical agent testing involving IDOR, SSRF, metadata, sandbox, and credential failures [record_id:2209], plus a secure-by-design Kubernetes debugging demonstration [record_id:2218]. The [un]prompted records contrast confidential AI’s TEE-based protection [record_id:2343] with fast AI-assisted AWS privilege escalation and blockchain-backed C2 [record_id:2355].

BSidesLV 2025 supplies a practical defensive layer. It distinguishes product, application, and platform security [record_id:2384]; demonstrates secretless AWS/Azure Kubernetes authentication with IRSA, Workload ID, and Terraform [record_id:2396]; uses Kubernetes and cloud credits for inexpensive secret scanning [record_id:2408]; scopes shadow cloud with Luminaut [record_id:2414]; applies Kyverno and KubeArmor [record_id:2429]; builds an open-source code-to-cloud toolchain [record_id:2440]; examines ordinary Kubernetes configuration hazards [record_id:2446]; and demonstrates seccomp hardening [record_id:2456].
